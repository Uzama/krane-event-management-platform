# ADR 0001 — Router: stdlib `net/http.ServeMux`, via oapi-codegen's `std-http-server` target

**Status:** Accepted (item 05)

## Decision

Route requests with Go's standard library `net/http.ServeMux` (Go 1.22+ pattern matching, e.g. `POST /v1/events/{eventId}/sessions`), generated by `oapi-codegen`'s `std-http-server` target from `openapi/openapi.yaml`.

## Alternative rejected

A third-party router — `chi` and `gorilla/mux` were the two considered. Both are mature, both integrate with `oapi-codegen`, and either would have worked.

## Why

- `CLAUDE.md`'s stack rule is explicit: prefer the standard library; ask before adding any dependency. Go 1.22 made method + wildcard route patterns (`{id}`) a stdlib feature — the exact thing `chi`/`gorilla` used to be needed for.
- One fewer dependency in the request path of every single endpoint, for auth/authz/idempotency middleware that already has to be hand-written per `CLAUDE.md`'s architecture — the router itself doesn't need to pull its weight beyond routing.
- `oapi-codegen`'s stdlib target was not assumed to work — item 04 left it as an explicitly open question ("item 05 must verify oapi-codegen targets `net/http.ServeMux` before writing code, or reopen the router choice"), and item 05 confirmed it by actually generating code and inspecting the output, not by reading documentation. Had it not worked cleanly against `ServeMux`, this decision would have been reopened.

## Consequence

Middleware composition (request-id → recover → auth → authz → idempotency) is hand-rolled as a small chain of `http.Handler` wrappers rather than a router-provided middleware stack. This is a small amount of extra code, once, in `internal/http/middleware/`, in exchange for one less dependency touching every request.
