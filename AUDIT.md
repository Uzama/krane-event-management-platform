## 2026-08-23 22:40 — Feature 02 · DDL / schema migrations

Completed feature 02. One timestamped golang-migrate pair, `migrations/20260823164421_init_schema.{up,down}.sql`, carrying all nine tables from `docs/requirements.md` §2 — `users`, `events`, `event_members`, `role_permissions`, `rooms`, `sessions`, `invitations`, `audit_log`, `idempotency_keys` — with `uuidv7()` PKs, `timestamptz` throughout, `events.timezone` holding an IANA name, and session time as a single `tstzrange`.

`version` and `deleted_at` columns ship now; both partial `EXCLUDE` constraints are deferred to item 16, with their exact DDL sitting in a comment on `sessions`, so 16's race test can fail for the right reason before it passes. `role_permissions` is created empty — item 07 seeds it.

Introduced the two-role model the rest of the project depends on. `krane_migrator` owns the database and every object the migrations create; `krane_app` is the API's runtime identity. **Item 03 must set `POSTGRES_USER=krane_migrator` in compose and point the API DSN at `krane_app`** — `ALTER DEFAULT PRIVILEGES` says `FOR ROLE krane_migrator` explicitly, and if migrations ever run as a different role every future table reaches the API with no grants. `krane_app` is created with `LOGIN` and no password; item 03 sets it from the environment rather than committing a credential to a migration.

Two tables are special-cased away from the blanket DML grant, each with its own grant and its own unconditional `REVOKE` as the last statements of the file: `audit_log` is `INSERT, SELECT` only (append-only is a grant, not a convention), and `role_permissions` is `SELECT` only — the API reads the policy that governs it and cannot rewrite its own permission rules. Both revokes are order-independent by design, so a later reordering or a future blanket grant cannot silently widen them.

Three decisions were recorded in the docs rather than left implicit: **D9** — soft-deleting a session releases its room and speaker slot immediately, stated as a product rule in `docs/requirements.md` §7.3 (new) and referenced from the `deleted_at` legend line in `docs/er-diagram.md`, because item 16's partial `EXCLUDE` makes it true whether or not anyone intended it; **D10** — `event_members.role` and `invitations.role` are `CHECK`-constrained while `role_permissions.role` deliberately is not, since that table is the registry (for item 24's ADR); and the half-open `[)` range convention, documented as a column comment on `sessions.time_range` so items 12 and 16 build back-to-back sessions that do not falsely conflict.

Verification, in place of the `make test` that does not exist until item 03: fourteen gates against a throwaway `postgres:18` (18.6) container started with `POSTGRES_USER=krane_migrator`, then torn down. Two gates ran *before* any DDL was written — `uuidv7()`'s exact signature was confirmed from `pg_catalog` rather than assumed (zero-arg form; an `interval`-shifted overload also exists), and extension ordering was proven in both directions (a `citext` column without the extension errors; dropping `citext` while such a column exists errors, and `CASCADE` would take the column with it). The rest: nine tables present, zero naive timestamp columns, `tstzrange`/`citext` where the design says, v7 version nibble on generated ids, all six unique constraints, the `role_permissions` composite PK, the role `CHECK` rejecting `'organiser'` and accepting `'contributor'`, the audit and policy privilege matrices, live `permission denied` on `UPDATE`/`DELETE`/`TRUNCATE` of both protected tables while connected **as `krane_app`**, and `[)` back-to-back ranges proven not to overlap where `[]` would.

The `ON SEQUENCES` default grant was dropped after confirming the schema owns no sequences — zero sequences, zero identity columns, zero `serial` columns — but its `REVOKE` is kept in the down file as a deliberate no-op so a future sequence grant cannot strand `DROP ROLE`. That the default-privileges revokes are load-bearing was proven, not assumed: stripping them makes the down migration fail at `DROP ROLE` with a non-zero exit rather than continuing. Full `up → down → up` round trip is clean — down leaves zero tables, zero roles, zero extensions and zero default-ACL entries, and the second up restores all nine tables with the privilege matrix intact.

Gate 10 exercises FK cascade on a hard `DELETE FROM events`. It is a safety net only: events are soft-deleted, so that path does not run in normal operation and it is not evidence that deleting an event is handled — that is items 08 and 22.

No `FAILURES.md` rule added: nothing went wrong that isn't already an invariant in `CLAUDE.md`.

## 2026-08-23 23:55 — Feature 03 · docker-compose + Makefile + green pipeline

Completed feature 03. `make up && make seed && make test` — the contract the assignment is graded on — now runs green from a clean machine in **1m25s cold** (no cached images) and **14s warm**, against the five-minute budget. A fresh-clone rehearsal from the staged index, with no `.env` and no setup step, passes identically.

`docker-compose.yml` runs `postgres:18.6` and `ghcr.io/navikt/mock-oauth2-server:2.1.10` long-running, plus two one-shot services behind a `tools` profile: `migrate` (`migrate/migrate:v4.18.1`) and `app-role`. Every tag is pinned and was manifest-checked for linux/arm64 **and** linux/amd64, so the dev Mac and `ubuntu-latest` run identical images. One-shots are invoked with `docker compose run --rm` rather than `up --wait`, because `--wait` treats a service that exits as a failure — which is exactly what a one-shot does on success.

All three obligations item 02 left behind are honoured: `POSTGRES_USER=krane_migrator` (so `ALTER DEFAULT PRIVILEGES FOR ROLE krane_migrator` binds to the role that actually creates the objects), every host-facing DSN points at `krane_app`, and the `app-role` service sets `krane_app`'s password from the environment via psql's `:'app_password'` quote-and-escape form — no credential in a migration, and no string-concatenation into DDL.

**`make up` is idempotent; `make down` is the only destructive target.** This is load-bearing rather than stylistic: `make test` depends on `up`, so an `up` that wiped volumes would destroy what `seed` just wrote before `test` ever saw it — at item 14 that is 50k invitations vanishing silently mid-chain. Proven by inserting a row, re-running `up`, and reading it back. `CLAUDE.md` described `up` as a "clean start", which is the wording that would have tempted a future session to break exactly this; it was corrected in this commit, along with the now-false "repo is pre-code" note.

The one test is `migrations/schema_test.go`, and it is deliberately not a tautology. It connects to the throwaway `krane_test` **as `krane_app`** and asserts three things, each proving a different link in the pipeline: `current_user` is the runtime role (not the owning migrator, for whom `has_table_privilege` would return true for everything and make the next assertion vacuous); all nine tables exist; and the **privilege matrix** landed too — `audit_log` is SELECT+INSERT but not UPDATE/DELETE, `role_permissions` is SELECT only. That third assertion is the one that earns its keep: grants are per-database, so a migration that created every table in `krane_test` while silently skipping every GRANT and REVOKE would sail past a schema-only check, and every later authz and audit test would then be running against privileges the API does not have in production.

Each assertion was proven load-bearing by breaking its subject and watching it fail: pointing the DSN at `krane_migrator` (fails on `current_user`), dropping `idempotency_keys` (fails on the table list), hand-granting `UPDATE ON audit_log` (fails on the privilege matrix), and supplying a DSN password that does not match what `app-role` set (fails with SQLSTATE 28P01). Note that `KRANE_APP_PASSWORD=wrong make test` **passes**, and correctly so — `make up` re-applies the password from the same variable, so both ends move together; the mismatched-DSN case is what actually demonstrates enforcement.

Test-DB isolation was decided now rather than deferred, because every later package inherits it: one `krane_test` today, the standing rule that no test may assume sole occupancy of the database, and `CREATE DATABASE <pkg> TEMPLATE krane_test` per package from the first data-writing package (item 08) — a template clone is a file copy, so migrations run once for the whole suite rather than once per package. Isolation is per-package and never per-test, since item 16's race test needs two goroutines contending on the same rows. All three rules are now in `CLAUDE.md` so they cannot be re-litigated.

Dev credentials are guarded by a target, not a comment: `make up` refuses to start when `ENV=production` while `POSTGRES_PASSWORD` or `KRANE_APP_PASSWORD` still holds its committed default. Verified in both directions. `.env.example` carries a banner stating the file is committed and every value in it is public.

The Go version lives in exactly one place. `go.mod` is the source of truth; `scripts/require-go.sh` parses the `go` directive out of it rather than taking a version argument, and CI uses `setup-go` with `go-version-file: go.mod`. Nothing to keep in step by hand.

`.github/workflows/ci.yml` runs `make lint && make test` on push and PR, with `docker compose logs` on failure. **It has not executed yet** — a workflow cannot run until the branch is pushed, so it is reviewed and YAML-validated, not proven. `make lint` (gofmt + `go vet` + a pinned `golangci/golangci-lint:v1.62.2-alpine`, so local and CI run byte-identical versions) is green locally.

Two things were learned the hard way and are logged rather than quietly fixed. `ISSUE.md` carries the first: Postgres 18 refuses to start on `/var/lib/postgresql/data`, the path every older Postgres uses and every tutorial repeats — the familiar pattern was reached for and 18 rejected it, which is exactly the trap the brief warns about. The second is in `FAILURES.md`: `pgx/v5` was pinned at v5.7.6, not the current v5.10.0, because v5.8.0 onward require Go 1.24/1.25 while this repo is pinned to 1.23 — a module needing a newer Go than `go.mod` declares fails to resolve outright rather than degrading.

Deliberately out of scope, and noted so the gaps are not mistaken for oversights: no `api` service in compose (there is no `cmd/api` until item 04, which adds it; `docs/components.md` §3 already shows it in the target topology), `make seed` is a stub that names item 14, and the OIDC service has no compose healthcheck because the image ships without a shell — `make up` polls its discovery document from the host instead, and item 06 configures the issuer properly.

## 2026-08-24 01:25 — Feature 04 · Repo architecture scaffolding

Completed feature 04. `cmd/`, `internal/utils`, `internal/container`, `internal/http` (+ `handler`, `response`), and `internal/bootstrap` now exist and are wired end to end: `cmd/api/main.go` derives a `signal.NotifyContext` and calls `bootstrap.Boot(ctx)`, which loads `utils.Config` from the environment, builds a `container.Container` (pgx pool + `log/slog` JSON logger), mounts `internal/http.NewRouter` (stdlib `net/http.ServeMux` — no new dependency; Go 1.23's method+pattern routes are enough for one route), and serves `GET /health` until the context is cancelled, at which point `http.Run` shuts down gracefully. `domain/` and `adapter/` deliberately stay empty this feature — neither has a consumer yet (`domain/errors.go` lands with 07, `domain/opt` with 12/20, `adapter/postgres` with 08, `adapter/auth` with 06); creating them now would be placeholder packages with no logic and no test.

`GET /health` is a readiness check, not mere liveness: it pings the db pool through a local `Pinger` interface (`type Pinger interface { Ping(ctx context.Context) error }`) that `*pgxpool.Pool` satisfies structurally, so `internal/http` never imports `pgx` even transitively — the template every later handler should copy (depend on the narrowest interface, not a concrete adapter type). Failure returns 503 through the one error envelope from `CLAUDE.md` (`internal/http/response`, introduced here rather than as a later stub), with `details` always rendering as `{}`, never omitted.

`internal/utils/db.go`'s `NewPool` fails fast and is bounded twice over: `pgxpool.ParseConfig` + `ConnConfig.ConnectTimeout = 5s` bounds the dial, and the pool's own startup `Ping` runs under a second `5s` context. Both are proven, not assumed: the fail-fast tests (`utils`, `container`, `bootstrap`) point at a local `net.Listen` that never calls `Accept` — the kernel completes the TCP handshake into the backlog (genuinely routable/connectable) but nothing ever speaks the Postgres protocol back, reproducing "routable but dead" deterministically on loopback rather than depending on how the sandbox's network handles an unroutable IP. All three assert the failure returns in well under the test's own bound, not never.

Graceful shutdown lives in `internal/http/server.go`'s `Run(ctx, srv, ln, logger)`, decoupled from `bootstrap` so it's unit-testable on its own terms: `TestRun_GracefulShutdown` binds an ephemeral port, dials it to prove the server is really serving, cancels the context, and asserts both that `Run` returns and that the port stops accepting connections afterward — shutdown proven as a behavior, not just "returns nil." `NewServer` sets `ReadHeaderTimeout`/`ReadTimeout`/`WriteTimeout`/`IdleTimeout` rather than leaving `http.Server` at its zero-value (unbounded) defaults.

`docker-compose.yml` gains the `api` service item 03 flagged as owed, built from a new root `Dockerfile` (multi-stage, pinned `golang:1.23.12-alpine3.22` → `alpine:3.22.5`, exact patches confirmed to exist on Docker Hub before pinning — same discipline as the rest of the stack's images). It is **not** part of `make up`'s default set: `make test` runs `go test ./...` directly against Postgres on the host, the same pattern `migrations/schema_test.go` already established, so the graded pipeline never needs a containerized API process. The service exists for `docker compose up api` / a full local-stack run, matching `docs/components.md`'s topology — verified manually (`docker compose build api && docker compose up api`, `curl /health` → 200, real container-to-container DB connectivity). `.env.example` and the `Makefile` gained `HTTP_PORT`, `LOG_LEVEL`, `API_PORT` following the existing `POSTGRES_PORT`/`OIDC_PORT` naming pattern. `go.mod` picked up `pgxpool`'s own transitive deps (`puddle/v2`, `x/sync`) as indirect requires — no new top-level dependency, and `go.sum` had no diff (the hashes were already present under `pgx/v5`).

Verification: `make test -race` green across all seven packages (`bootstrap`, `container`, `http`, `http/handler`, `http/response`, `utils`, `migrations`); `make lint` green (gofmt/govet/golangci-lint, including errcheck/bodyclose/rowserrcheck — no ignored errors anywhere in the new code). Manual sanity beyond the automated suite: `go run ./cmd/api` against the real dev stack → `curl /health` → 200; Postgres stopped mid-run → 503 with the standard envelope; `SIGINT` → `"shutting down"` log line → clean exit, no hang.

## 2026-08-24 07:17 — Feature 05 · OpenAPI harness

Completed feature 05. `openapi/openapi.yaml` (OpenAPI 3.0.3) is now the documented contract, starting with `GET /health` — `HealthStatus{status,database}` on 200, the shared `ErrorEnvelope` (matching `internal/http/response/error.go` field-for-field) on 503. `openapi/spec.go` embeds it (`//go:embed`) so nothing downstream depends on a filesystem path. From here, every endpoint updates the spec first.

Item 04's carried-forward question — whether oapi-codegen actually targets stdlib `net/http.ServeMux` — is answered: it does, cleanly. `internal/http/gen` (generated via `internal/tools/tools.go`'s pinned `oapi-codegen/v2 v2.6.0`, driven by `//go:generate` in `internal/http/gen/generate.go`) uses the `std-http-server` target, producing a `ServerInterface` and `HandlerFromMux`/`HandlerWithOptions` that default to `http.NewServeMux()` — confirmed by actually running the generator and inspecting its output, not by reading docs. `internal/http/router.go` is unchanged in behavior; its comment now records the choice as confirmed rather than open.

`internal/http/validator` is the `CLAUDE.md`-named validation package: `LoadSpec`/`ValidateRequest`/`ValidateResponse` wrap `kin-openapi`'s `openapi3filter` and `routers/legacy` (the router-agnostic path matcher — chosen specifically to avoid a routing-framework dependency, since this package only ever runs inside tests). Per FEATURES.md's literal wording ("wired into tests"), validation is **not** live production middleware: `router.go`'s production request path is untouched. `internal/http/router_test.go` boots the real, unmodified router and validates the **live recorded** 200 and 503 responses against the spec, so spec/handler drift is caught in either direction — this, plus `internal/http/validator/validator_test.go`'s negative-path proofs (`POST /health` has no matching route; a response missing a required field is rejected), is what "CI verifies the server actually honours the spec" means here.

CI's other half is drift detection: `make generate` regenerates `internal/http/gen` from the spec; `make contract-check` runs it and then `git diff --exit-code -- internal/http/gen openapi` — proven, not assumed, by deliberately editing the spec without regenerating (fails, diff shown) and reverting (passes again). `.github/workflows/ci.yml` runs it as a new `Contract check` step, after `Lint` and before `Test`, so drift fails fast before the Docker/Postgres stack spins up.

Two dependencies were added — `github.com/oapi-codegen/oapi-codegen/v2 v2.6.0` (tool only, via `internal/tools`) and `github.com/getkin/kin-openapi v0.133.0` — chosen after an explicit decision **not** to bump the Go toolchain: an earlier draft of this feature proposed moving `go.mod` to Go 1.25 to reach the newest oapi-codegen/kin-openapi releases (which require 1.24/1.25), but that was rejected — a dependency's own `go` directive is a floor for the toolchain, not a mandate to raise this module's declared version, and nothing in this API needs OpenAPI 3.1. `go.mod`, `pgx`, `golangci-lint`, and the Docker base images are all untouched.

That rejection paid for itself during verification: pinning `kin-openapi` to v0.135.0 (the newest release whose own `go` directive still resolves against 1.23) compiles fine in isolation but **breaks oapi-codegen v2.6.0's own source** (`pkg/codegen/schema.go` assumes an older `openapi3.SchemaRef.Ref` field shape) once both land in the same module graph — caught by actually running `go build`/`go vet`/the codegen tool in a scratch module, not by checking `go` directives alone. Letting `go mod tidy` resolve the minimum compatible version naturally lands on v0.133.0, which builds, vets, and generates real output cleanly. The same round of verification cut a dependency that had been planned: `oapi-codegen/nethttp-middleware` only wraps *requests* as production middleware (which this feature doesn't use) and can't validate responses either way, so `internal/http/validator` calls `kin-openapi`'s `routers/legacy` + `openapi3filter` directly instead — one fewer dependency than originally planned.

`make lint` (golangci-lint v1.62.2, unchanged) passes on all new code including the generated `health.gen.go`, with no new `.golangci.yml` exclusion — its default generated-file detection (the `Code generated ... DO NOT EDIT` header) was enough. `go vet` shows no deprecation warning on the `routers/legacy` import. `make test` is green across all packages including the two new ones.

No `FAILURES.md` line added: the two things that went sideways during planning — the Go-1.25 ripple effect, and the kin-openapi/oapi-codegen version mismatch — were both caught before any code shipped, not after a runtime failure.
