Completed feature 02. Introduced the two-role model the rest of the project depends on. `krane_migrator` owns the database and every object the migrations create; `krane_app` is the API's runtime identity. **Item 03 must set `POSTGRES_USER=krane_migrator` in compose and point the API DSN at `krane_app`** — `ALTER DEFAULT PRIVILEGES` says `FOR ROLE krane_migrator` explicitly, and if migrations ever run as a different role every future table reaches the API with no grants. `krane_app` is created with `LOGIN` and no password; item 03 sets it from the environment rather than committing a credential to a migration.

Two tables are special-cased away from the blanket DML grant, each with its own grant and its own unconditional `REVOKE` as the last statements of the file: `audit_log` is `INSERT, SELECT` only (append-only is a grant, not a convention), and `role_permissions` is `SELECT` only — the API reads the policy that governs it and cannot rewrite its own permission rules. Both revokes are order-independent by design, so a later reordering or a future blanket grant cannot silently widen them.

Three decisions were recorded in the docs rather than left implicit: **D9** — soft-deleting a session releases its room and speaker slot immediately, stated as a product rule in `docs/requirements.md` §7.3 (new) and referenced from the `deleted_at` legend line in `docs/er-diagram.md`, because item 16's partial `EXCLUDE` makes it true whether or not anyone intended it; **D10** — `event_members.role` and `invitations.role` are `CHECK`-constrained while `role_permissions.role` deliberately is not, since that table is the registry (for item 24's ADR); and the half-open `[)` range convention, documented as a column comment on `sessions.time_range` so items 12 and 16 build back-to-back sessions that do not falsely conflict.

**`make up` is idempotent; `make down` is the only destructive target.** This is load-bearing rather than stylistic: `make test` depends on `up`, so an `up` that wiped volumes would destroy what `seed` just wrote before `test` ever saw it — at item 14 that is 50k invitations vanishing silently mid-chain. Proven by inserting a row, re-running `up`, and reading it back. `CLAUDE.md` described `up` as a "clean start", which is the wording that would have tempted a future session to break exactly this; it was corrected in this commit, along with the now-false "repo is pre-code" note.

The one test is `migrations/schema_test.go`, and it is deliberately not a tautology. It connects to the throwaway `krane_test` **as `krane_app`** and asserts three things, each proving a different link in the pipeline: `current_user` is the runtime role (not the owning migrator, for whom `has_table_privilege` would return true for everything and make the next assertion vacuous); all nine tables exist; and the **privilege matrix** landed too — `audit_log` is SELECT+INSERT but not UPDATE/DELETE, `role_permissions` is SELECT only. That third assertion is the one that earns its keep: grants are per-database, so a migration that created every table in `krane_test` while silently skipping every GRANT and REVOKE would sail past a schema-only check, and every later authz and audit test would then be running against privileges the API does not have in production.

## 2026-08-24 08:35 — Feature 06 · Auth (validate-only)

Completed feature 06. `internal/domain/` and `internal/adapter/` exist for the first time. `internal/domain/user` is the aggregate: `entity.go` (`User`, `Claims` — the latter deliberately living in domain, not `adapter/auth`, so `http/middleware` can depend on the same type both `adapter/auth` produces and `domain/user.Service` consumes without ever importing `adapter` directly), `port.go` (`Repository`), `service.go` (`GetOrCreateBySubject`, a thin pass-through — the atomicity guarantee belongs to Postgres, not application code), and `errors.go` (`ErrTokenInvalid`, `ErrMissingClaims` — two new sentinels, not the four `ErrConflict`/`ErrVersionMismatch`/`ErrForbidden`/`ErrNotFound` named in `CLAUDE.md`'s target layout, which stay deferred to item 07, their first real consumer).

`internal/adapter/postgres/user_repo.go` implements the upsert as `INSERT ... ON CONFLICT (subject) DO NOTHING RETURNING ...`, falling back to a plain `SELECT` only when the insert affected nothing — the `INSERT` is the one atomic decision point; the fallback `SELECT` never decides anything, so there's no check-then-act window. **Decision, not an oversight:** `email`/`name` are captured once, at row creation, and never refreshed on a later sign-in — proven by a test that signs in twice with a *different* email/name the second time and asserts the row is untouched. Re-syncing profile fields on every login would reopen `users.email`'s unique-constraint conflict case (two subjects claiming the same new email) for no benefit a validate-only feature needs; revisiting this is a fair scope item for whichever later feature actually needs live profile sync.

`internal/adapter/auth/verifier.go` wraps `github.com/coreos/go-oidc/v3` (pinned `v3.13.0` — the newest version whose own `go` directive still resolves at our `go 1.23.0`; the latest, v3.20.0, requires `go 1.25.0`). Audience checking is enforced explicitly (`oidc.Config{ClientID: audience}`, never `SkipClientIDCheck`) — the plan review flagged this as the single most likely "your auth has a hole" gap, and it's covered by a dedicated wrong-audience test, not just implied by the code. Every verification failure returns one of `user.ErrTokenInvalid` (bad signature, expired, wrong audience, wrong issuer — "someone sent garbage") or `user.ErrMissingClaims` (verifies cleanly but lacks `sub`/`email`/`name` — "the issuer isn't sending what we require"), a distinction `http/middleware/auth.go` surfaces as a structured `reason` log field (`token_invalid` vs `missing_claims`) while still returning 401 either way — the HTTP contract doesn't change, but item 08's on-call debugging can tell a forged token from an issuer misconfiguration at a glance.

`internal/http/middleware/auth.go` follows the `Pinger` pattern from item 04: two narrow local interfaces (`TokenVerifier`, `UserResolver`), never a concrete adapter type, so `http` still never imports `adapter`. `Auth()` attaches the resolved `user.User` to the request context (`UserFromContext`); every rejection path — missing header, malformed header, verifier error, resolver error — returns 401 through the standard envelope, proven never to panic into a 500 by dedicated tests for each path.

Two dependencies added: `github.com/coreos/go-oidc/v3 v3.13.0` and its own direct dependency `github.com/go-jose/go-jose/v4 v4.0.5` (used directly in test code to mint/sign tokens against a local fake JWKS double — the same JOSE library go-oidc verifies against, not a second crypto library). Both, plus their transitive `golang.org/x/oauth2`/`x/net`/`x/crypto`, resolve cleanly at `go 1.23.0` with no toolchain bump (`GOTOOLCHAIN=local`, confirmed via `go build`/`go vet` in isolation before writing any consuming code — same discipline item 05 recorded). No change to the Go toolchain, `pgx`, `golangci-lint`, or the Docker base images.

`docker-compose.yml`'s `oidc` service now carries a `JSON_CONFIG` (empirically verified against the exact pinned `mock-oauth2-server:2.1.10` image, not just its docs, by running it standalone first) with four claim mappings: three fixed demo identities (`demo-admin`/`demo-contributor`/`demo-attendee`, matched on `client_id`) for `make token`, and one test-only `test_sub`/`test_aud` templated mapping so Go integration tests can mint a token for an arbitrary, unique subject — and deliberately wrong audiences — without touching the three fixed identities. **Caught before it shipped:** Docker Compose interpolates `${VAR}` in every compose-file string value, including this multi-line one, before the container ever sees it — the first version of this config silently defaulted `test_sub`/`test_aud` to blank strings, discovered only by minting a token and decoding it. A retry (a row already exists) compares `request_hash`: a match replays the stored `response_body` verbatim (decoded, never recomputed); a mismatch returns `domain.ErrConflict`, mapped to `422 idempotency_key_conflict` at the handler -- reusing the existing four-sentinel error set per call-site convention (room.go's own precedent) rather than adding a fifth domain error.

Three requirements were held to explicitly, each with its own proof, not just satisfied incidentally:
